# Abstraction Catalog

Manually curated catalog of reusable abstractions extracted during REFACTOR passes,
for discovery by future Coder/Refactor agents. Add to the appropriate section below
when extracting a genuinely reusable abstraction.

> Note: this repository also maintains a separate, broader, **auto-generated**
> project-wide symbol index at `docs/catalog/` (regenerated by
> `scripts/update_catalog.py`, requires `ANTHROPIC_API_KEY` for description
> generation). That index indexes *every* public symbol project-wide; this file
> is narrower and intentionally curated — it exists specifically to flag DRY
> extractions and the established conventions behind them, with enough context
> that the next node implementation doesn't reinvent the same pattern. Do not
> let the two drift into contradiction; prefer checking both when in doubt.

## Error handling / retry policy mapping

Convention: each infrastructure-facing error enum defined in the `pipeline`
crate implements its own `retry_policy(&self) -> RetryPolicy` inherent method,
co-located with the enum definition, so callers map errors the same way
regardless of which operation failed.

| Name | Kind | Location | Description | Tags |
|------|------|----------|-------------|------|
| `LlmError::retry_policy` | method | `pipeline::tools` | Maps an `LlmError` variant to a `RetryPolicy`; rate-limited/5xx/network errors are `Retryable`, schema/context-window/4xx errors are `NonRetryable`. The original convention this pattern follows. | error-handling, retry, llm |
| `DomainServiceError::retry_policy` | method | `pipeline::domain_services` | Maps a `DomainServiceError` variant to a `RetryPolicy`; connection-failed/service-unavailable are `Retryable`, everything else `NonRetryable`. | error-handling, retry, domain-service |
| `GitHubOperationError::retry_policy` | method | `pipeline::github` | Maps a `GitHubOperationError` variant to a `RetryPolicy`; `Transient`/`RateLimitExhausted` are `Retryable`, `NotFound`/`PermissionDenied`/`ParseFailure`/`SdkCapabilityMissing` are `NonRetryable`. Extracted during the Intake node REFACTOR pass (#58) — the GREEN implementation had reinvented this mapping as a node-local free function (`nodes::intake::github_error_retry_policy`) instead of following the established per-error-enum convention; moved onto the enum itself so any future node calling `IssueTracker` methods (Planning, Spawning, Architecture, Review — all still `todo!()`) can call `err.retry_policy()` directly instead of recreating the match. | error-handling, retry, github |

**When implementing a new node that calls an infrastructure trait method returning one of these error types:** call `err.retry_policy()` directly — do not write a local match arm. If you need this mapping for an error enum that does **not** yet have a `retry_policy` method, add one next to the enum definition in `pipeline`, following this same shape, rather than writing an ad hoc free function in `nodes`.

## Context package assembly

| Name | Kind | Location | Description | Tags |
|------|------|----------|-------------|------|
| `estimate_token_count` | fn | `pipeline::context` | Rough token estimate (~4 bytes/token) for a text string. Use when building a `ContextItem`/`ContextPackage` by hand outside `assemble_context` — e.g. a node with no context packs to assemble yet (Intake is the first node in the pipeline and has none). Was previously module-private and had been re-implemented inline in `nodes::intake::build_context_package` with a slightly different (char-count vs byte-length) formula; made `pub` and reused during the Intake node REFACTOR pass (#58). | context, token-estimation, llm |

**When implementing a node that needs to wrap raw text (not a context pack) into a `ContextPackage` for an `LlmGateway::call`:** build the `ContextItem`/`ContextPackage` struct literal directly (see `nodes::intake::build_context_package` for the shape) and call `pipeline::estimate_token_count` for the token count — do not re-derive the ~4-bytes-per-token estimate inline. If the node *does* have context packs available, use `ContextAssembler`/`pipeline::assemble_context` instead; this helper is specifically for the no-packs-yet case.

## Test fixtures (nodes crate)

| Name | Kind | Location | Description | Tags |
|------|------|----------|-------------|------|
| `sha256_hex` | fn | `nodes::executor` (`pub(crate)`) | Computes a SHA-256 hex digest; mirrors `pipeline::security`'s private hashing helper so hashes computed in test fixtures and in `DefaultNodeRunner`/`run_step_with_runner` production code agree. Previously duplicated verbatim in `gateway_tests.rs`, `executor_tests.rs`, and (as of the GREEN implementation for #58) `intake_tests.rs`; widened from module-private to `pub(crate)` during the Intake node REFACTOR pass and all three test files now import the single copy instead of redefining it. The underlying cross-crate duplication against `pipeline::security`'s own (unexported) hashing helper remains a separately tracked, deliberately deferred finding — not addressed here since fixing it means changing `pipeline::security`'s public API, out of scope for a REFACTOR pass. | test-fixture, hashing |

**When writing a new test fixture in the `nodes` crate that needs a SHA-256 hex digest** (e.g. a `ConstitutionalRules::source_hash` or `PipelineStateComment::graph_hash` fixture): `use crate::executor::sha256_hex;` — do not paste a new copy of the digest helper.
