Implement `ArchitectureNode::execute` (`crates/nodes/src/architecture.rs`), completing the architectural design phase of a pipeline run. The Architecture node is no longer a `todo!()` stub — it is the second node in the default 7-node pipeline (after Intake) and will now actually run: it loads context packs for the classified work item, validates cross-domain interface constraints, assembles LLM context (pyramid summaries, interface definitions, matched Context Pack guidance), calls the LLM to generate a Markdown architecture document, runs deterministic alignment checking against the declared node inputs, and — when the work item is safety-affecting — also runs LLM-semantic alignment and folds its results into the traceability matrix. Operators running a pipeline that reaches this node need a valid `.cogworks/constitutional-rules.md` file in the repository (already required by every node via the executor's step-1 load, but now visibly exercised for the first time by an implemented LLM-calling node after Intake); a missing or invalid file halts the run before any LLM call is made.

A Security Reviewer audit during this change found and fixed three High-severity issues, all included in this release:

- **Constitutional rules are now genuinely operator-reviewed.** `ArchitectureNode::execute` (and `NodeRunner::run_node`) now receive the real `ConstitutionalRules` value loaded once per pipeline step from the approved branch, instead of a self-built, always-valid placeholder the node previously constructed internally. A tampered or stale rules document is now rejected before any LLM call this node makes, rather than being silently bypassed. See ADR-0009 (`docs/adr/ADR-0009-thread-constitutional-rules-into-node-execute.md`) for the full rationale.
- **All LLM calls across the pipeline are now scanned for prompt-injection patterns before being sent to the provider.** `LlmGateway::call` scans every piece of assembled context for known injection patterns and fails closed with a new `LlmError::InjectionDetected` error — the provider is never called on that path. This is a security hardening, not a feature regression, but it means a call that previously succeeded can now fail if genuinely adversarial content (e.g. an issue body or file content crafted to override the system prompt) appears anywhere in the assembled context. Operators should expect this new failure mode to surface occasionally on legitimately adversarial input, and should not treat it as a transient error — `InjectionDetected` is non-retryable, since retrying resubmits the same content and re-triggers the same detection.
- **Cross-domain constraint and alignment failures now carry full structured detail into the pipeline's error/audit trail**, not just a violation count — operators and automated rework loops reading a `NodeFailed` error now see the actual finding detail (check type, misalignment kind, description, blocking flag) needed to act on the failure, instead of a bare count.

### Judgment call on bump type

Both packages are pre-1.0 (`0.1.0`) internal workspace crates not yet published or consumed outside this repository's own `cli` composition root (which is not yet wired to either the executor or this node — tracked separately). Two of the changes above are breaking in a strict semver sense for any external consumer: `ArchitectureNode::execute` and `NodeRunner::run_node` each gained a trailing `rules: &ConstitutionalRules` parameter, and `pipeline::LlmError` gained a new `InjectionDetected` variant (breaking for any exhaustive `match` without a wildcard arm). Per 0.x semver convention, and because there is no external consumer of these APIs today, this is released as `minor` rather than `major` for both crates. Revisit this convention once either crate reaches `1.0.0` or gains an out-of-workspace consumer.
